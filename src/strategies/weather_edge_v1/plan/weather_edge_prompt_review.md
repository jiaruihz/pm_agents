# Weather Edge V1 - 专家审查与提示词强化报告

## Part 1: 高级量化分析与 LLM 提示词专家审查诊断

这份策略的底层商业逻辑非常清晰且稳健。作为一个“人机协同”、“只做尾部 No 策略并且严防错锚”的项目架构，从防灾/风控的角度挑不出大的逻辑硬伤。但是，如果 **`SKILL.md` 是作为 AI/模型的入口指令**，它目前的行文还有一些“过于拟人化”，在约束力和结构性上存在优化空间。

### 1. 业务逻辑与量化风控视角的优点与潜在盲点
- ✅ **绝对优秀的定力**：“不代替人下单”、“不轻易动用浏览器（浏览器只做fallback）”、“同站点 WU History 才是最终结算值”。这几个核心原则完美切中了预测市场特别是 Polymarket 这种易发生“错定/错源”事件的痛点。这种人机协同是当前最高效的路线。
- ✅ **逻辑隔离好**：用明确的文件切分层级：`DATA_SOURCE.md` 定源的阶级，`DECISION_WORKFLOW.md` 定分析链路，`city/*.yml` 定原子数据，`SKILL.md` 只做执行总纲。这种设计比“一个长 prompt 走天下”要强一万倍。
- ⚠️ **潜在盲点 - 缺乏对幻觉的硬防御**：策略中最常出问题的是数据缺失。当 WU/天气站拿不到目标日期的小时预报时，LLM **极有可能会根据当前温度加上历史常识，自己推断出一个最高温并塞进数据里（编造数据幻觉）。** 现有的 `SKILL.md` 告诉了 LLM 怎么查，但没有用强烈的禁止语（Negative Prompt）去封杀幻觉。

## Part 4: 终极解法——“双文件物理隔离”架构 (Human & Machine Separate Setup)

如果“混合提示词”依旧让你觉得阅读体验不够纯粹，或者约束力打折扣，那么**“搞两个文件，一个给人看、一个给机器看”这是目前 Agentic System 里最成熟的架构模式（分离关注点，Separation of Concerns）**。

这个套路的优势无穷大：
1. **给人的文档 (`README.md` 或 `MANUAL.md`)**：可以写满“来龙去脉”、“历史经验”、“为什么以前踩过坑”，全是大白话。
2. **给机器的文档 (`SKILL.md` 或 `SYSTEM_PROMPT.md`)**：去掉所有废话，全用冷冰冰的指令（Directives）、条件触发（If-Then）、JSON Schema 和黑名单（Blacklist）构成。AI 执行效率翻倍，且再也不会因为读了长篇大论而注意力失焦（Attention Drift）。

### 如何解决“同步修改”的问题？
通过**在两个文件头部互相建立“强引用断言（Assertion）”**。

这就像代码里的接口与实现：你告诉大模型，“如果我（人类）叫你修改业务逻辑，你必须**同时、严格对齐地**修改这两个文件，否则算作严重违规”。

## Part 5: 高级延展 - 策略、Agent 架构的进阶优化点

如果你想把这套系统做到“无可击破”，除了提示词改法，在 **策略本身与 Agent 的全局设计上**，还有下面这几块高价值的改进空间（你可以看情况“往里加”）：

### 一、 策略体系设计层面 (Alpha & Risk)

1. **量化“分歧”与“信心指数”(Confidence Scoring)**
   - **现状**：你们用到了“分歧是否接近 2 档”这种经验描述。
   - **优化**：在 JSON 输出中要求系统算出一个 `Confidence Score (0-100)` 或 `Divergence Variance (误差方差)`。比如，当主锚 WU 是 44、AccuWeather 是 43 时，Agent 不只要能看懂差了1度，还要能在历史基线上判断出“下午 3 点前这 1度 分歧的消散概率”。如果误差方差超出阈值，系统状态直接进入 `halt`。

2. **增加“时间轴衰减 (Time Decay)”的显式管理**
   - **现状**：知道临近尾盘要主动撤退，但没有数学模型。
   - **优化**：盘口价值随着时间推移是递减的。目前 `DECISION_WORKFLOW.md` 对时间戳有记录，但需要把“当前时间距离峰值时间的剩余小时数”作为一个核心参数传入 Agent 决策里。例如：“如果在距离峰值仅剩 2 小时，且目标温度只差 0.5度，强行熔断”。

3. **对冲或双边锁仓逻辑（Optional）**
   - 如果市场有足够的流动性（目前可能不适用极端尾部），但如果是主流动区，当天气剧烈波动时，是否允许 Agent 给出某种 Pair Trading 或 Spread 锁仓的建议？（这是更长远的方向）

### 二、 Agent 架构与调用链路层面 (Agentic Architecture)

1. **“自我怀疑与纠错机制” (Self-Correction Loop / Reflection)**
   - **现状**：单趟流程（抓取 -> 提取 -> 吐出诊断）。
   - **优化**：设计一个审查钩子。例如在最后输出 `action_suggestion` 是 `maker_entry_ok` 时，加一个内建的检查：它必须自己问自己：“我的依据数据（WU主锚）是几分钟前获取的？有没有过时？是否已核实完全”。如果不确信，它必须去重新抓一次确认。这是 Agent 防低级失误的最强绝招。

2. **基于历史错误池的“动态 Few-Shot”注入**
   - **现状**：靠 `city/*.yml` 和全局文档防错。
   - **优化**：如果有过具体的血泪教训（比如某个机场晚上会有怪异的海风导致温度异常），不要全堆在系统 Prompt 里，会导致 Prompt 爆炸。可以写个小脚本：当查询具体的某个城市时，去一个叫 `blunders.db` (错误库) 里把该城市或该季节的典型出错案例作为 Few-Shot Examples 动态抽屉塞进 Prompt。大大提高单城市的判断准确率。

3. **多模型交叉会诊 (Multi-Agent Consensus)**
   - 既然追求绝对安全、只吃尾部，那么任何单模型的“抽风”都是致命的。
   - **核心设计**：你可以拉起一个便宜的小模型（如 Haiku 或 GPT-4o-mini）专门负责干脏活——提取网页数字。然后再用主力推理模型（Claude-3-Opus 或 GPT-4o）去根据提取的结构化数字跑策略判定。如果两边拿到的数字对不上，立马告警。这种“Extractor Agent”与“Decision Agent”的物理隔离，比让一个庞然大物既当矿工又当裁判要稳健得多。

### 三、 交互与日志机制 (Traceability)

1. **从“事后看日志” 到 “全量重放 (Replay) 支持”**
   - 策略的进步靠复盘。目前有 `runtime/weather_decision_journal.db`，但对于多变的天气盘。
   - 必须强制 Agent 在吐出关键结论时，**附带一个快照哈希 (Snapshot Hash) 或者关键页面的截图地址/Raw HTML 存档**。当你事后发现判定出错时，能把当时的整个环境完全恢复出来让它重写逻辑，而不是“死无对证”。
